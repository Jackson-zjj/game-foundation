# GameFoundation 项目定位与设计约定

## 1. 项目定位

GameFoundation 是通用游戏系统框架，采用核心代码与引擎、平台适配层分离的结构。

目标是在开发不同游戏项目时，复用已经实现的系统，通过配置和扩展补充具体游戏的规则，减少重复开发。框架既包含基础能力，也可以包含背包、属性、任务等可选玩法模块。

首个接入目标是 Unreal Engine 的 C++ 游戏项目。核心代码以独立 C++ 实现为起点，Lua 的职责和接入方式后续根据实际需求确定。

**当前状态：已实现独立 C++ 核心构建、基础背包模块和对应测试。UE 适配插件、Lua 接入及其他系统仍处于规划阶段。** 本文中的系统范围和目录布局为目标设计，具体已实现功能见 [README](../README.md)。引擎版本和平台支持范围以实际构建与运行验证为准。

## 2. 仓库职责

本仓库主要承担三项职责：

1. 提供可在多个游戏中复用的系统规则、数据结构和接口。
2. 提供核心系统连接具体引擎、平台所需的适配代码和构建配置。
3. 提供文档、测试和使用示例，使系统能够被接入、验证和维护。

实际游戏的内容由游戏仓库管理，包括关卡、剧情、角色、数值配置、美术资源，以及项目特有的玩法。

通用模块允许提供默认规则，但应能被具体游戏配置或扩展。是否提取一个模块，以实际复用价值为依据，避免在缺少需求时一次性建设所有候选系统。

## 3. 核心代码与适配层的边界

### 3.1 核心代码

核心代码负责可以独立表达的游戏规则和数据处理。例如，物品如何堆叠、任务进度如何变化、属性修正如何计算。

核心代码应满足以下约定：

- 不直接依赖 UE 或其他引擎的头文件、对象类型、容器和运行时。
- 不直接调用具体平台的 SDK 或 API。
- 不引用某个游戏项目的角色类型、配置或资源。
- 需要存储、时间等外部能力时，通过明确的接口或参数获取。
- 能在不安装 UE 的环境中独立编译、运行和测试。

“核心独立”是代码依赖关系上的约定，不能仅通过移动文件或拆分目录实现。

### 3.2 引擎适配层

引擎适配层负责将核心系统接入引擎的对象、生命周期和运行机制。UE 适配层可能包含：

- 插件描述文件、模块定义和构建配置。
- C++ 核心与 UE 对象、组件、Subsystem 等机制的连接。
- 与 UI、输入、音频、资源加载、地图切换等引擎能力的连接。
- 核心数据与引擎类型之间的转换，以及事件通知。

优先使用引擎已有能力，再根据框架需要提供一致的调用方式。使用 UMG、GAS 等 UE 能力形成的实现，应归入 UE 适配或扩展部分；这些实现本身仍然依赖 UE。

### 3.3 平台适配层

平台适配层负责接入平台服务，例如账号登录、存储、云存档、成就、排行榜和支付。根据项目需求逐项增加，不要求每个平台具备相同能力。

引擎与平台是两个不同维度：UE 是游戏引擎；TapTap 是游戏分发与服务平台；微信小游戏是游戏运行环境。UE 开发与 TapTap 发布可以同时成立，微信小游戏则需要验证对应引擎和代码的运行、导出与接入方案。

### 3.4 依赖方向

适配层依赖核心定义的接口和数据，核心不反向引用具体适配实现。游戏项目负责选择模块、组织配置，并连接需要的适配层。

例如，核心定义“保存数据”所需的接口，由具体适配实现文件存储或平台存储，再将实现传入使用方。

## 4. 系统范围

下表为候选范围，具体模块按实际项目需求实现。属于同一功能的代码，也可能分布在核心和适配层中。

### 4.1 基础能力

| 系统 | 适合复用的职责 | 与具体环境相关的部分 |
| --- | --- | --- |
| 配置与数据管理 | 数据结构、标识、查询约定、合法性检查 | 引擎配置资源的读取和转换 |
| 存档 | 存档数据、版本迁移、保存与恢复的约定 | 文件读写、平台存储、云服务 |
| 设置 | 设置项、取值约束、默认值和变更通知 | 应用音量、画质、语言等设置 |
| UI | 可复用的界面状态与流程约定 | 界面实例、布局、渲染和输入焦点 |
| 输入 | 需要跨项目统一的动作与模式约定 | 按键映射、设备输入和引擎输入系统 |
| 音频 | 分类、播放请求和切换规则 | 声音资源、播放和混音 |
| 资源与地图加载 | 加载请求和流程约定 | 引擎资源引用、异步加载与地图切换 |
| 本地化 | 文本标识、语言选择与查询约定 | 引擎本地化资源和界面刷新 |

每项能力只提取确有价值的共同部分。对于高度依赖引擎的能力，初期可以直接在引擎适配层提供实现。

### 4.2 可选玩法模块

| 系统 | 框架可提供的通用部分 | 游戏项目负责的内容 |
| --- | --- | --- |
| 属性 | 属性计算、修正和变更通知 | 属性定义、公式和成长配置 |
| Buff / 状态 | 持续时间、叠加、刷新和周期效果 | 具体状态效果与表现 |
| 技能 | 释放条件、消耗、冷却和阶段规则 | 具体技能行为、动画和表现 |
| 物品与背包 | 添加移除、堆叠、容量和使用接口 | 物品配置、使用效果和界面 |
| 装备 | 装备槽、条件检查、替换和属性修正 | 装备内容、规则配置和表现 |
| 任务 | 状态、进度、条件和奖励接口 | 任务内容与剧情 |
| 对话 | 节点、选项、条件和事件 | 台词、分支与演出 |
| 交互 | 交互条件与执行约定 | 目标检测、具体行为与提示表现 |
| 掉落与奖励 | 掉落表、权重和奖励发放规则 | 物品、概率和数量配置 |
| 生成 | 生成条件、数量限制和刷新规则 | 引擎对象生成、关卡位置与表现 |

玩法模块应允许按需选择。例如，使用背包系统不应被迫依赖任务或技能系统。

## 5. 目录规划

以下为目标布局，目录随真实代码和文档逐步建立，尚未实现的模块无需提前创建占位内容。

```text
game-foundation/
|-- README.md
|-- CMakeLists.txt
|-- core/
|   |-- include/gamefoundation/
|   `-- src/
|-- adapters/
|   |-- engines/
|   |   `-- unreal/
|   |       `-- GameFoundation/
|   |           |-- GameFoundation.uplugin
|   |           |-- Source/
|   |           `-- Content/
|   `-- platforms/
|       |-- taptap/
|       `-- wechat/
|-- tests/
`-- docs/
    `-- project-overview.md
```

- `core/`：独立于引擎和平台的 C++ 代码及公共接口。
- `adapters/engines/`：引擎插件、桥接代码和相关构建配置。
- `adapters/platforms/`：平台服务接入代码；按目标环境选择语言和构建方式。
- `tests/`：核心规则与模块间约定的验证。
- `docs/`：定位、设计、构建、接入和使用说明。
- `CMakeLists.txt`：独立构建核心和测试；UE 接入还需要对应的模块构建配置。

仓库、代码及资源目录使用英文命名，文档正文可以使用中文。仓库名 `game-foundation` 与框架名、UE 插件名 `GameFoundation` 分别遵循各自的命名习惯，无需完全一致。

## 6. 语言与跨环境复用

第一阶段以纯 C++ 核心和 UE 适配层验证整体结构。是否引入 Lua，以及哪些规则由 Lua 承担，应在实际需求明确后决定。

跨引擎复用与跨语言复用需要分别处理：

- 纯 C++ 核心可以解除对 UE 的依赖，但目标环境仍需支持相应的编译和运行方式。
- 在微信小游戏等环境中使用 C++，需要验证 WebAssembly 等路线及对应的桥接和构建条件。
- Lua 代码需要兼容的运行时和接入方式，不能假定所有引擎、平台均能直接运行。
- 使用 TypeScript 等其他语言的项目，需要通过桥接复用已有代码，或另行实现相同规则。

目录分离不会自动完成这些工作。只有在目标环境中验证通过后，才将其列为已支持环境。

## 7. 与游戏仓库的关系

框架仓库：[Jackson-zjj/game-foundation](https://github.com/Jackson-zjj/game-foundation)。

游戏仓库：[Jackson-zjj/my-game](https://github.com/Jackson-zjj/my-game)。

框架维护共用能力，游戏维护实际内容。框架通过接口、配置和事件支持扩展，不直接依赖游戏仓库中的代码或资源。

### 7.1 通过 Git 子模块接入

游戏仓库可将框架检出到 `External/GameFoundation`：

```text
MyGame/
|-- MyGame.uproject
|-- Source/
|-- Content/
`-- External/
    `-- GameFoundation/
```

子模块记录框架仓库地址和具体提交 ID。游戏可以固定使用一个已经验证的框架版本，随后按需升级。其他游戏可以使用不同版本，彼此独立。

子模块目录是框架仓库的一份工作目录，可以直接修改并在当前游戏中联调。如果另有独立的框架检出目录，两份检出应通过 Git 提交同步。

### 7.2 提交与推送的影响

| 操作 | 影响 |
| --- | --- |
| 提交游戏仓库 | 记录游戏改动，以及所使用的框架提交 ID |
| 推送游戏仓库 | 更新游戏远程仓库 |
| 修改子模块中的框架代码 | 改变框架的本地工作区，当前游戏可能立即使用这些代码 |
| 在框架目录中提交 | 创建框架自己的本地提交 |
| 在框架目录中推送 | 更新框架远程仓库 |

只修改游戏时，提交游戏即可。同时修改框架和游戏时，应先提交并推送框架，再提交游戏改动及新的框架版本记录，最后推送游戏。

上述行为按普通 Git 操作描述。额外设置的递归推送或自动化脚本可能触发其他操作。子模块可能检出为 detached HEAD，开发前应先切换或创建工作分支。

### 7.3 UE 接入

框架根目录包含核心与多个适配目录，因此 UE 插件位于 `adapters/engines/unreal/GameFoundation`，而非仓库根目录。

UE 游戏需要配置插件搜索路径、启用插件，并在使用插件类型的游戏模块中声明模块依赖。适配层还需要配置核心代码的编译或链接；仅设置插件目录不会自动编译外部 C++ 核心。

Git 依赖接入与 UE 编译接入是两个步骤，应分别验证。

## 8. 实施顺序

1. 建立仓库文档与依赖关系，明确核心、适配层和游戏项目的职责。
2. 建立独立 C++ 构建，以一个小型背包模块验证添加、移除、堆叠和容量规则。
3. 在不启动 UE 的情况下编译、运行并验证核心逻辑。
4. 建立 UE 适配插件，让实际游戏能够调用核心，并验证两者的连接。
5. 根据游戏开发中的实际需求增加模块；在确定第二种目标环境后，验证同一核心代码的复用路线。

首个里程碑是：核心可独立运行、UE 可调用核心、两个仓库可分别维护，并能从版本记录恢复完整依赖。
